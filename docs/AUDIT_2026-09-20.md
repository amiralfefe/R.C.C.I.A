# Audit R.C.C.I.A - 20 septembre 2026

## Perimetre et verdict

Audit du monorepo, de ses quatre pipelines specialises, du hub MultiCancer et du
packaging de deploiement. Demonstrateur educatif / portfolio uniquement : aucun
diagnostic, aucune validation clinique, aucune recommandation medicale.

Base inspectee : `a323780ae5a7fbf52c12015a6c84d4aab921c1c2`, branche `main`,
initialement propre. Le tag `multicancer-v1` reste sur
`a51772da5d50eb8d758c01d737ea09f2f388cea6`.

**AUDIT TERMINE - BLOQUANTS RESTANTS** : la demonstration publique refuse
l'acces au depot Hugging Face des checkpoints. Les corrections de cet audit
sont locales, non commitees et non deployees. Aucun modele, score experimental,
checkpoint ou dataset reel n'a ete modifie. Aucun nouvel entrainement reel.

## Architecture inspectee

- Quatre packages PyTorch specialises : Leukemia, LungColon, Breast, Metastasis.
- MultiCancer selectionne explicitement un projet, et un mode pour LungColon.
- Un ModelManager par session charge un seul adaptateur a la fois. Ce n'est pas
  une limite globale de modeles ou de memoire pour tout le processus serveur.
- Les images passent par un decodeur commun borne, puis le preprocessing et
  l'inference specialises. Grad-CAM explique une classe, pas une causalite.
- Le bootstrap telecharge cinq checkpoints depuis un depot HF prive vers des
  chemins fixes. Le token reste cote serveur. Aucun upload de checkpoint public.
- Pas d'API REST metier, de base de donnees, de comptes applicatifs ou de paiement.
  Les controles SQL, roles utilisateurs, transactions et pages 404 metier sont N/A.

## Dependances et securite

92 versions installees ont ete interrogees via l'API JSON PyPI, 92 reponses obtenues.
Il ne s'agit pas d'une execution de pip-audit ni d'une attestation du cloud.
Sources : [API PyPI](https://docs.pypi.org/api/json/) et
[base d'avis Python](https://github.com/pypa/advisory-database).

| Paquet local | Constat | Traitement |
| --- | --- | --- |
| Pillow 12.2.0 | Avis multiples, dont parseur EPS avant filtre de format. | 12.3.0 installe ; exigences racine/deploiement actualisees ; relecture PyPI sans avis pour cette version. |
| anyio 4.14.1 | Avis publies, correctifs annonces en 4.14.2. | Chemins concernes non exposes par le code applicatif observe ; mise a jour separee a valider. |
| GitPython 3.1.50 | Avis publies, correctifs annonces jusqu'a 3.1.60. | Pas d'arguments Git arbitraires acceptes par le hub ; suivi necessaire. |
| pip 26.1.2 | Avis de traitement d'URL d'index, correctif annonce en 26.2. | Outillage, pas une route publique ; non modifie. |
| setuptools 65.5.0 | Plusieurs avis, dernier correctif indique en 83.0.0. | Outillage ancien ; upgrade majeur non applique silencieusement. |
| torch 2.12.1 | CVE-2025-3000, torch.jit.script, correctif indique en 2.13.0. | Pas d'appel jit.script observe ; aucune migration risquee du couple torch/torchvision. |

Le cas EPS est decrit par l'[avis officiel Pillow](https://github.com/python-pillow/Pillow/security/advisories/GHSA-pg7v-jwj7-p798).
Le decodeur acceptait des octets inconnus dans Image.open avant de verifier
PNG/JPEG. La correction limite les parseurs des les deux ouvertures ; elle
complete la mise a jour Pillow. Le test de non-dispatch est non destructif.
L'[issue PyTorch](https://github.com/pytorch/pytorch/issues/149623) porte sur
une autre surface : ne pas assimiler tout avis de paquet a une faille du hub.

Les limites existantes de taille, dimensions, pixels et nombre de frames sont
conservees. Le serveur limite maintenant l'upload a 8 Mio. CORS et XSRF restent
aux valeurs protectrices par defaut. Pas de quota global d'inference ni de test
de saturation : plusieurs sessions peuvent encore consommer trop de RAM/CPU.

Scan par motifs sur les fichiers suivis : aucun token HF/Kaggle/GitHub ou bloc
de cle privee detecte. Scan des noms : aucun poids, token ou secret suivi.
Verification finale : 242 fichiers suivis ou nouveaux examines ; aucun motif
de secret detecte. Les 70 fichiers Markdown ne contiennent aucun lien relatif
rendu casse (exemples en blocs de code exclus). Les chemins sensibles de controle
sont bien ignores par Git.
Cela ne couvre pas tout l'historique Git, tous les formats de secrets, ni les logs
et secrets distants. Le telechargement utilise toujours les checkpoints du
proprietaire : aucune provenance tierce non fiable ne doit etre ajoutee.

Aucun nom de fichier commun entre splits detecte. Ce n'est pas une preuve

Le [papier LC25000](https://arxiv.org/abs/1912.12142) decrit l'augmentation de
1250 images en 25000 : le split aleatoire actuel ne garantit pas l'independance
des images sources. La documentation LungColon signale explicitement cette limite.

Le preprocessing train/evaluation/inference a ete inspecte : normalisation et
resolution compatibles avec les pipelines/checkpoints. Aucun poids ni resultat
historique n'a ete remplace. Les probabilites softmax ne sont pas une confiance
clinique calibree. Le cas Breast incorrect a forte confiance est conserve.

Le choix du meilleur modele ou seuil en regardant le test est exploratoire et
peut biaiser la selection. Une future etude devrait choisir sur validation puis
evaluer une seule fois sur test independant. Le champ PR-AUC Metastasis utilise
average_precision_score (average precision), pas une integration trapezoidale.
Les seuils illustrent FP/FN, sans proposer de seuil medical.

## Actions restantes et limites de la verification

1. Le proprietaire doit verifier dans Streamlit Cloud Secrets que HF_MODEL_REPO_ID
   designe le depot prive voulu et qu'un HF_TOKEN de lecture valide y a acces.
   Ne jamais envoyer le token dans une conversation ou le mettre dans Git.
2. Une fois le patch relu et sa publication autorisee, le deployer puis refaire
   les cinq parcours publics ; les correctifs locaux ne protegent pas encore le cloud.
3. Tester sur un telephone physique et avec les aides d'accessibilite si leur prise
   en charge est revendiquee. Choisir licence et mentions d'operateur avant redistribution.

Non verifies : build Docker propre, nouvelle installation vierge, charge hostile,
session cloud administrateur, tous les navigateurs, lecteur d'ecran, historique
complet de secrets, tous les doublons de datasets, validation clinique et ensemble
des dependances transitives distantes. Aucun nettoyage de donnees reelles.
La revue source est une passe ciblee sur les frontieres principales et les scripts
de donnees, pas une preuve ligne par ligne de tous les fichiers. La delegation
independante a echoue sur une limite d'usage ; revue poursuivie par l'agent principal.
La relecture shell du repertoire temporaire du plugin de securite, initialement
bloquee par une limite d'usage, a ensuite ete autorisee : les trois artefacts
canoniques du scan ont ete verifies presents. Le serveur local de test a ete arrete.

Le projet est exploitable localement comme portfolio avec ces reserves, mais
**la demonstration publique n'est pas validee en l'etat**.
